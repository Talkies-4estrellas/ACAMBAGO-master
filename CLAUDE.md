### Auth (Clerk)

This project uses **Clerk**, not Supabase Auth. `src/proxy.ts` protects `/dashboard`, `/admin`, `/perfil`. Sign-in/sign-up pages are custom (`(auth)/login`, `(auth)/register`), not Clerk's default `/sign-in`/`/sign-up` routes — the `NEXT_PUBLIC_CLERK_SIGN_IN_URL`/`SIGN_UP_URL` env vars point to them. Because of Clerk, all Supabase tables have RLS **disabled** (see `supabase/clerk-migration.sql`) — authorization is enforced in API routes and client code, not Postgres policies.

**An admin's only panel is `/admin` (since 2026-09-18) — no buyer profile, no seller panel.** `(public)/perfil/layout.tsx` is a thin async server component that checks the role with Clerk + Supabase and `redirect("/admin")`s before rendering anything else (the actual interactive UI moved unchanged to `perfil/PerfilShell.tsx`, a client component the layout renders as a child); `dashboard/layout.tsx` does the same `redirect("/admin")` for admins, unconditionally, before its business-ownership checks. An admin manages their own name/phone/avatar from a "Mi perfil" tab inside `/admin` itself (`admin/AdminProfileSection.tsx`, adapted from the buyer's `perfil/configuracion/page.tsx` but without demo mode or the "Crear tienda" card), not from `/perfil/configuracion`. **Not verified live** with a real admin session — a test via direct Supabase REST write was blocked by Claude Code's own permission classifier; verified by code review only (same `role === "admin"` pattern already proven elsewhere).

`layout.tsx` passes `esES` from `@clerk/localizations` to `ClerkProvider` for a Spanish UI, but that package ships `formFieldInputPlaceholder__signUpPassword` (the sign-*up* password field's placeholder, distinct from the sign-*in* one which is translated) as `void 0` — confirmed still untranslated even in the latest published version (4.17.0) as of 2026-09-15, a real upstream gap, not a version-lag issue. Fixed by spreading `esES` into a local `clerkLocalization` object with that one key overridden ("Crea una contraseña") instead of waiting on Clerk to fix it.

### Demo Mode

All demo data lives in `src/lib/demo-data.ts`. Demo businesses have fixed IDs (`demo`, `demo-lavado`, etc.) and their own routes under `(public)/business/`. `BusinessCard` maps these IDs to their routes via a `demoSlugs` lookup. The home page merges demo businesses with Supabase results, filtering out any Supabase business whose ID starts with `demo`. Demo data never touches the database — it's a fallback for running the app without any credentials configured.

When Supabase credentials **are** configured (as in this deployment), real businesses/products/orders exist alongside the demo ones. `IS_DEMO` (checked via `NEXT_PUBLIC_SUPABASE_URL`) gates whether a given page reads real data or falls back to demo data.

### Orders

Checkout groups cart items by `business_id` and calls the `create_order_with_items` Postgres RPC (see `supabase/orders-rpc.sql`) once per business — order + items are inserted in a single transaction, so a failed item insert can't leave an order with zero products. The seller's `dashboard/business/orders` page subscribes to Supabase Realtime on `orders` INSERT and plays a beep (Web Audio API, no audio file) + shows a toast when a new order arrives.

- **Real security bug (2026-09-25): `create_order_with_items` trusted the price the client sent for every item.** It read `p_items[].price` straight from the checkout instead of comparing it against `products.price` server-side — unlike the coupon redemption flow (`redeem_coupon`), which already computes everything on the server. Since the RPC has `GRANT EXECUTE` for `anon` and the anon key is public, anyone could call it directly (bypassing the checkout UI entirely) with any price they wanted. Fixed with `supabase/orders-trusted-price.sql` (replaces `create_order_with_items`, same signature, no checkout changes needed): it now ignores the client-sent price/name entirely and re-reads them from `products`, joining each `product_id` against `products.business_id = p_business_id` (which also blocks smuggling another business's product into an order), recomputes subtotal/total server-side, and requires a positive quantity per item (without that check a negative quantity would still yield a negative total even with the real price, and would add stock back instead of subtracting it). Verified live: a direct RPC call with a real product (price $100) but a forged `price: 1` and `quantity: 2` still produced an order with the real $200 total; negative quantity and cross-business products are both rejected with a clear exception.

### Sistema de Apartados (layaway con anticipo, added 2026-09-25)

**Por qué existe**: el usuario quiere invertir la prioridad de venta del proyecto — el carrito/checkout de arriba sigue funcionando igual, pero pasa a ser la última opción. El flujo principal ahora es: el catálogo y el mapa funcionan sobre todo como un **directorio** para ubicar la sucursal física real de una tienda; el comprador le **pregunta** a la tienda (esto ya existía: `MessageSellerButton.tsx`, usado en la ficha de producto y en el perfil del negocio, ya deja escribirle a una tienda con o sin un producto asociado — cubre tanto "pregunto por este producto" como "no lo encontré, ¿lo tienen?"); si el vendedor confirma que lo tiene, el comprador lo **aparta** pagando un anticipo, y el vendedor decide si lo manda a la sucursal más cercana al comprador (para que ahí lo recoja) o si lo envía él mismo a domicilio; el saldo se paga después, por transferencia o en persona.

Tres decisiones del usuario, confirmadas antes de diseñar nada (vía `AskUserQuestion`, en modo plan):
1. **Sin inventario real por sucursal.** La app solo registra a qué sucursal quiere ir el comprador (`reservations.branch_id`, nullable = "sucursal principal", útil porque `business_branches` sigue vacía en la base real, nadie ha dado de alta una sucursal todavía); el traslado físico entre sucursales lo maneja el vendedor por su cuenta, la app no lo valida ni lo rastrea.
2. **El "no lo encontré, ¿lo tienen?" se resuelve dentro de Mensajes**, no en una bandeja nueva — de ahí que el botón "Crear apartado" viva dentro del chat del vendedor en vez de ser una pantalla aparte.
3. **El anticipo es configurable por producto** (`products.deposit_amount`, `NULL` = ese producto no admite apartado), no un monto fijo de tienda.

**`supabase/reservations.sql`**: agrega `products.deposit_amount NUMERIC(10,2)` (con un `CHECK` de que sea mayor a 0 y no mayor al precio) y la tabla `reservations` (RLS deshabilitado, mismo patrón de todo el proyecto; agregada a la publicación `supabase_realtime`). Un apartado puede nacer de a) un producto real de catálogo (`product_id NOT NULL`, precio/anticipo se vuelven a leer de `products` del lado del servidor, nunca del cliente — mismo principio que el arreglo de arriba) o b) algo que el vendedor confirma por chat que tiene aunque no esté subido (`product_id NULL`, el vendedor define nombre/precio/anticipo al vuelo). Tres RPC:
- `create_reservation(p_origin, ...)` — `p_origin='catalog'` exige que quien llama sea el propio comprador y relee precio/anticipo reales; `p_origin='custom'` exige que quien llama sea el `owner_id` del negocio (revalidado dentro de la función, no solo en la ruta — mismo patrón de defensa en profundidad que `redeem_coupon` con `p_scanning_owner_id`) y requiere `conversation_id`. Rechaza cantidad ≤ 0.
- `update_reservation_status(...)` — el vendedor avanza el estado (`reservado → listo_en_sucursal` si es `pickup_branch`, o `→ enviado_a_domicilio` si es `home`, luego `→ entregado`) o cancela; el comprador solo puede cancelar el suyo. Un apartado `entregado`/`cancelado` rechaza cualquier cambio nuevo.
- `mark_reservation_payment(...)` — el vendedor marca `deposit_paid_at`/`balance_paid_at` a mano (verificación manual de transferencia o cobro en persona, sin gateway).

**Rutas de API** (`src/app/api/reservations/`, patrón de `coupons/validate/route.ts`: Clerk `auth()` → cliente server → `supabase.rpc(...)` con `p_actor_user_id` siempre igual al `userId` de Clerk): `create/route.ts` (arma los parámetros según `origin`, valida ownership para `custom` antes de llamar el RPC, notifica al vendedor si es `catalog` o posta un mensaje de chat vía `sendMessage()` si es `custom` — sin tocar `ChatThread.tsx`, que no tiene slot para acciones especiales), `status/route.ts` (determina si quien llama es vendedor o comprador comparando contra `businesses.owner_id`/`reservations.user_id`, notifica a la otra parte o posta un mensaje si hay `conversation_id`), `payment/route.ts`. Ninguna ruta usa segmentos dinámicos `[id]` (el proyecto no tiene ese patrón en `src/app/api` — todas las rutas existentes pasan el id en el query string o en el body), así que estas tampoco: el id va en el body (`reservation_id`).

**UI nueva**: campo "Monto de anticipo para apartado" en `dashboard/business/products/page.tsx` (mismo patrón nullable que "Cantidad en inventario", justo después del precio); botón "Apartar con $X de anticipo" en `(public)/product/[id]/page.tsx` (solo si `product.deposit_amount != null`, `ReserveProductButton.tsx`); botón "Crear apartado" en `dashboard/business/mensajes/[id]/page.tsx` (junto al header del chat, abre `CreateReservationModal.tsx` para artículos fuera de catálogo); `ReservationStatusBadge.tsx` (mismo patrón que `OrderStatusBadge.tsx`). Dos pantallas nuevas con Realtime: `(public)/perfil/apartados/page.tsx` (comprador, tab "Mis apartados" en `PerfilShell.tsx`, después de "Mis mensajes") y `dashboard/business/apartados/page.tsx` (vendedor, item "Apartados" en `DashboardNav.tsx`'s `navItems`, entre Pedidos y Cupones — deliberadamente **no** agregado a `pendingItems` ni al bottom nav móvil de `dashboard/layout.tsx`, ambos son listas curadas que ya excluyen cosas como Mensajes/Preguntas). `NotificationType` se extendió con `"new_reservation"`/`"reservation_status"`; los `iconFor()` de las 2 pantallas de notificaciones ya tenían un `if`-chain con fallback genérico, así que solo se les agregó un `if` más para el ícono `Bookmark`, sin romper nada.

### QR Coupon Flow

1. Business creates coupon → `generateCouponCode()` produces `ACAM-XXXXXX`
2. QR payload: `JSON.stringify({ coupon_code, business_id })`
3. Client scans with `html5-qrcode` in `QRScanner.tsx`
4. POST to `/api/coupons/validate` → verifies ownership + validity, records redemption

### Key Patterns

- **CSS**: `@import url(...)` for Google Fonts must come before `@tailwind base;` in `globals.css`, or the build fails.
- **Images**: `next/image` is used everywhere; `product-images` and `business-images` are Supabase Storage buckets. Products can have multiple photos (`products.image_urls TEXT[]`, first item = cover/`image_url`), shown via `ProductGallery.tsx` (product page) and `MiniCarousel.tsx` (store cards, auto-advances every 2.5s).
- **Product reels**: `components/ui/ProductsReel.tsx` is the auto-scrolling horizontal carousel (`animate-reel` in `tailwind.config.ts`, pauses on hover) used for "Productos Destacados" on the home page and for each business's own "Productos" section. Optional `stock_quantity`/`is_available` on each item show an "Agotado" badge (disables `AddToCartButton`) or "Últimas X" near the price — callers that don't pass them keep the old behavior (no badge). Nav arrows call `scrollBy({behavior:"smooth"})` but must pause the auto-scroll ref first, or the per-frame `scrollLeft` write cancels the smooth scroll almost instantly. Cards no longer show a category badge (removed 2026-09-14, every screen that uses this component) — the category is only shown on the product's own detail page now. The title reserves 2 lines (`min-h-[2.5rem]`) and the "Agregar al carrito" button sits at `mt-auto` inside a `flex flex-col` card, so a 1-line title doesn't leave that card's button sitting higher than its neighbors in the same grid row.
- **Real bug (2026-09-23): `ReelCard`'s whole-card click target only worked over the text, not over the photo — on both the home page and `/productos` (same shared component, one fix covers both).** The invisible full-card `<Link>` (`absolute inset-0`) was declared *first* in the JSX, before the photo's `<div>`. That photo div is also `position: relative` (needed for the `fill` image) with no explicit `z-index`, which puts it in the same CSS stacking-order bucket as the Link's `z-0` — and within that bucket, whichever element comes *later* in the DOM paints on top and wins hit-testing. The photo div, appearing after the Link, sat on top and silently absorbed clicks that should have reached the Link underneath. The text block below it is a plain unpositioned `<div>`, which always paints *beneath* any positioned element — so the Link stayed on top there, which is why clicking the name still worked. Fixed by moving the `<Link>` to the *end* of the card's JSX instead of the start — last-in-DOM-order now wins the tie against the photo, no `z-index` needed. `FavoriteButton`/`AddToCartButton` were untouched and still work correctly on top of everything, since they already had their own explicit `z-10`, which beats the Link regardless of DOM order. Rule of thumb for any future "whole-card invisible link" pattern: either declare the Link *last* in the JSX, or give it an explicit `z-index` higher than any other positioned-but-unindexed sibling — don't assume `position: absolute` alone makes an early-declared overlay win. `BusinessCard.tsx` uses a different, unaffected pattern (the `<Link>` literally wraps the whole card as its DOM parent, not an overlay sibling) and didn't need this fix.
- **`ProductGallery.tsx` has a Mercado-Libre-style hover lens + zoom panel, and a fullscreen lightbox (added 2026-09-23).** Hovering the main image tracks the cursor as a 0–1 percentage (`onMouseMove` against `imageBoxRef`'s bounding rect) and drives two things: a visible square "lens" overlay on the image itself (sized `LENS_SIZE = 1/ZOOM_FACTOR`, currently 2.2 → ~45% — reverted back to 2.2 after a false-start bump to 4 that the user didn't actually want), and a separate fixed-size (`w-80 h-80`, deliberately *not* matching the main image's size — that was the user's actual complaint, after an initial misread of "el recuadro del zoom" as the lens instead of this panel) `background-image` panel beside it using `background-size`/`background-position` percentages — the classic magnifier trick, no library. That panel needs its **own** `relative` wrapper distinct from the image box's — the image box has `overflow-hidden` (to crop-contain the photo) and positioning the panel `absolute left-full` *inside* it would clip the panel, since it renders outside the box's own bounds. Clicking the main image or any thumbnail (desktop rail or mobile row — thumbnails used to only swap the preview, now they also open the viewer, by explicit request) opens a `fixed inset-0` fullscreen viewer: counter, prev/next arrows, close button, Escape/ArrowLeft/ArrowRight keyboard support. Only the lens/panel are `hidden lg:block` (no room, no real hover on mobile); the lightbox itself works identically on mobile via tap.
- **Real bug (2026-09-23, found during the panel review): nothing in the app could ever cancel an order.** The `cancelado` status was fully wired everywhere it's *read* (the tab, `OrderStatusBadge`, excluded from `business-metrics.ts` and the seller's Resumen/Estadísticas, `checkout/tracking/page.tsx` already knew how to render its banner) but nothing ever *wrote* it — grep for `"cancelado"` across the app before this fix turned up zero write sites. Fixed by adding a "Cancelar pedido" button on both sides: `dashboard/business/orders/page.tsx` (next to the other status buttons, shown only while `pendiente`/`en_camino`, `confirm()`-gated, reuses `updateStatus` which already notified the buyer on any status change) and `checkout/tracking/page.tsx` (same visibility rule, its own `cancelOrder()`, `confirm()`-gated) — the buyer-side cancel needed a **new** notification to the seller that didn't exist before, added by extending the `businesses` join in that page to also select `owner_id` and calling `createNotification` with `type: "new_order"` (same type/pattern the checkout page already uses for "you have a new order", since there's no dedicated type for this and it's seller-facing exactly like that one).
- **Real bug (2026-09-23, found while adding the cancel buttons above): cancelling an order never gave back the stock it had reserved.** Stock is decremented at **order-creation** time, not at delivery (`create_order_with_items` in `supabase/products-stock.sql` — this part is intentional, kept as-is after asking the user, to avoid overselling while an order sits pending/en_camino), but no code path ever reversed that decrement. Fixed with `cancel_order_and_restore_stock(p_order_id)` (`supabase/cancel-order-restore-stock.sql`) — cancels the order and restores every item's `stock_quantity` in one atomic function, idempotent (a no-op if the order is already `cancelado`, so calling it twice never double-restores). Both cancel buttons call this RPC instead of a plain `.update({status: "cancelado"})` — every *other* status transition still goes through the plain update, only cancelling needs the stock side-effect.
- **`dashboard/business/orders/page.tsx`'s list now stays live across status changes, not just new orders (added 2026-09-23).** Its Realtime channel used to subscribe only to `event: "INSERT"` on `orders` — a status change on an order already in the list (the buyer cancelling from their own tracking page, the same order open in another tab/device) never showed up without a reload. Fixed with a second `.on("postgres_changes", { event: "UPDATE", ... })` on the same channel, which just patches that order's `status` in local state (everything else — customer, items — doesn't change on a status update, so no need to re-fetch). Deliberately did **not** add a new sound/toast for this — the existing "new order" beep (`OrderAlertListener` in `dashboard/layout.tsx`) is keyed off `INSERT` only, so there was no risk of double-firing it, but nothing equivalent was added for status changes either, since that wasn't asked for.
- **The buyer's own order list, `(public)/perfil/pedidos/page.tsx`, has the exact same live-update fix (added 2026-09-24, same root cause found the same way — reviewing the section, then confirming live by patching a test order's status via REST while the page sat open).** Same pattern: a second `useEffect` opens its own Realtime channel, `.on("postgres_changes", { event: "UPDATE", ... filter: "user_id=eq.<id>" })`, patching just `status` in local state. Deliberately **not** also listening for `INSERT` here — unlike the seller's list (which reasonably wants to see brand-new orders arrive live from any customer), a buyer placing a new order on another device while sitting on their own "Mis pedidos" list is a much rarer scenario, and it wasn't asked for.
- **Real bug (2026-09-24, found during the panel review): deleting a coupon never refunded the credit it consumed at creation.** Same shape as the 2026-09-23 stock bug (a reservation made at creation needs to be reversed on undo) but for `coupon_credits`, not `products.stock_quantity` — `deleteCoupon()` in `dashboard/business/coupons/page.tsx` was always a bare `confirm()` + `.delete()`, no code path anywhere restored the balance. Fixed with `supabase/coupon-delete-restore-credit.sql`: a `trg_restore_coupon_credit` trigger (`AFTER DELETE ON coupons`) that does `coupon_credits = coupon_credits + 1`, symmetric to `coupon-credits.sql`'s existing `trg_consume_coupon_credit` (`BEFORE INSERT`, `- 1`). Trigger-based like its sibling so the client-side `deleteCoupon()` needed **no changes at all** — the plain `.delete()` it already did is what fires the trigger. Verified live end-to-end (grant 1 credit → create a coupon, 1→0 → delete it, 0→1) after the user ran the migration in the SQL Editor.
- **Real bug (2026-09-24, found during the same review): the coupon "Vence" (expires) date always displayed one day earlier than what was actually saved.** `expires_at` always originates from an `<input type="date">` (a calendar day, no time component) but is stored as `TIMESTAMPTZ` midnight UTC — `new Date(coupon.expires_at)` then rendered via `date-fns`' `format()` (`CouponCard.tsx`) or `.toLocaleDateString()` (the public `/coupons` page's *own* local `CouponCard` function, which doesn't reuse the shared component and so needed its own fix) both format in the *local* timezone, and Mexico sits several hours behind UTC — pushing midnight UTC back into the previous local day. Fixed with `parseDateOnly()` in `src/lib/utils.ts`, which builds the `Date` from the string's year/month/day parts directly instead of letting the runtime reinterpret it as an instant; used in both of the places above. Any future code that renders `expires_at` (or any other date-only, `<input type="date">`-sourced column) as a calendar date must go through this helper, never a bare `new Date(iso)`.
- **`dashboard/business/products/page.tsx`'s list view has bulk actions (added 2026-09-23): checkboxes per row + a "select all on this page" checkbox in the header, and an action bar (Pausar/Activar/Eliminar/Cancelar) that appears once `selectedIds.size > 0`.** Grid view was deliberately left without this — the ask and the recommendation that led to it were both scoped to the list view specifically, matching its spreadsheet/POS framing. `selectedIds` is a plain `Set<string>` that persists across pagination (so selecting across pages before acting works), but gets cleared on any bulk action, and also when the tab or search filter changes (so it can never silently hold onto ids that have scrolled out of view). Bulk pause/activate is one `update(...).in("id", ids)`; bulk delete calls the *same* single-product `/api/products?id=` route once per id (still needed for its service-role Storage cleanup, see the delete-images bullet above) via `Promise.all`, and only removes from local state the ones that actually succeeded — a partial failure doesn't silently drop a product that's still real. The bulk-delete `confirm()` states the count, since it's irreversible and deletes Storage files too.
- **Categories (rewritten 2026-09-21, was a fixed list): dynamic table with parent/child hierarchy, ported from a sibling project's behavior ("Orden Express", `C:\nube` — outside this repo).** `supabase/categories.sql` (table `categories`: `id UUID`, `name`, `parent_id` self-reference, two case-insensitive partial unique indexes — one scoped to roots, one scoped per parent, seeded with the original 17 root names). `src/lib/categories.ts` (`normalizeCategoryName`, `buildCategoryTree`, `findOrCreateCategory`, `getCategoryTree`) and `src/lib/hooks/use-categories.ts` (`useCategories()` for client components).
