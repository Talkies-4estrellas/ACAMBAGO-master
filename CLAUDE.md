## Architecture

> Para contexto de negocio (qué se conectó, en qué orden correr el SQL, qué quedó pendiente), ver `DOCUMENTACION.md`.

### Route Groups

```
src/app/
  (public)/        ← Navbar + Footer layout; public pages
    page.tsx       ← Home / marketplace
    business/[id]/ ← Real business profiles (Supabase)
    business/demo* ← hardcoded demo pages (no Supabase)
    checkout/      ← Real checkout, writes orders/order_items via RPC
    map/           ← Leaflet map
  (auth)/          ← Centered card layout
    login/
    register/
  dashboard/       ← Sidebar + bottom nav layout (seller panel)
    business/      ← products, orders, coupons, reviews, analytics, settings
    PendingApprovalGate.tsx ← blocks the panel until admin approves the business
  admin/           ← Admin approval panel
  api/             ← Route handlers (coupons/validate, businesses, reviews, auth/callback)
```

### Auth (Clerk)

This project uses **Clerk**, not Supabase Auth. `src/proxy.ts` protects `/dashboard`, `/admin`, `/perfil`. Sign-in/sign-up pages are custom (`(auth)/login`, `(auth)/register`), not Clerk's default `/sign-in`/`/sign-up` routes — the `NEXT_PUBLIC_CLERK_SIGN_IN_URL`/`SIGN_UP_URL` env vars point to them. Because of Clerk, all Supabase tables have RLS **disabled** (see `supabase/clerk-migration.sql`) — authorization is enforced in API routes and client code, not Postgres policies.

**An admin's only panel is `/admin` (since 2026-09-18) — no buyer profile, no seller panel.** `(public)/perfil/layout.tsx` is a thin async server component that checks the role with Clerk + Supabase and `redirect("/admin")`s before rendering anything else (the actual interactive UI moved unchanged to `perfil/PerfilShell.tsx`, a client component the layout renders as a child); `dashboard/layout.tsx` does the same `redirect("/admin")` for admins, unconditionally, before its business-ownership checks. An admin manages their own name/phone/avatar from a "Mi perfil" tab inside `/admin` itself (`admin/AdminProfileSection.tsx`, adapted from the buyer's `perfil/configuracion/page.tsx` but without demo mode or the "Crear tienda" card), not from `/perfil/configuracion`. **Not verified live** with a real admin session — a test via direct Supabase REST write was blocked by Claude Code's own permission classifier; verified by code review only (same `role === "admin"` pattern already proven elsewhere).

`layout.tsx` passes `esES` from `@clerk/localizations` to `ClerkProvider` for a Spanish UI, but that package ships `formFieldInputPlaceholder__signUpPassword` (the sign-*up* password field's placeholder, distinct from the sign-*in* one which is translated) as `void 0` — confirmed still untranslated even in the latest published version (4.17.0) as of 2026-09-15, a real upstream gap, not a version-lag issue. Fixed by spreading `esES` into a local `clerkLocalization` object with that one key overridden ("Crea una contraseña") instead of waiting on Clerk to fix it.

### Demo Mode

All demo data lives in `src/lib/demo-data.ts`. Demo businesses have fixed IDs (`demo`, `demo-lavado`, etc.) and their own routes under `(public)/business/`. `BusinessCard` maps these IDs to their routes via a `demoSlugs` lookup. The home page merges demo businesses with Supabase results, filtering out any Supabase business whose ID starts with `demo`. Demo data never touches the database — it's a fallback for running the app without any credentials configured.

When Supabase credentials **are** configured (as in this deployment), real businesses/products/orders exist alongside the demo ones. `IS_DEMO` (checked via `NEXT_PUBLIC_SUPABASE_URL`) gates whether a given page reads real data or falls back to demo data.

### Supabase Clients

- `src/lib/supabase/client.ts` — browser client (Client Components)
- `src/lib/supabase/server.ts` — server client (Server Components, Route Handlers)
- `src/lib/supabase/middleware.ts` — session refresh only (no route protection; that's Clerk's `proxy.ts`)

### Orders

Checkout groups cart items by `business_id` and calls the `create_order_with_items` Postgres RPC (see `supabase/orders-rpc.sql`) once per business — order + items are inserted in a single transaction, so a failed item insert can't leave an order with zero products. The seller's `dashboard/business/orders` page subscribes to Supabase Realtime on `orders` INSERT and plays a beep (Web Audio API, no audio file) + shows a toast when a new order arrives.

### QR Coupon Flow

1. Business creates coupon → `generateCouponCode()` produces `ACAM-XXXXXX`
2. QR payload: `JSON.stringify({ coupon_code, business_id })`
3. Client scans with `html5-qrcode` in `QRScanner.tsx`
4. POST to `/api/coupons/validate` → verifies ownership + validity, records redemption

### Key Patterns

- **CSS**: `@import url(...)` for Google Fonts must come before `@tailwind base;` in `globals.css`, or the build fails.
- **Images**: `next/image` is used everywhere; `product-images` and `business-images` are Supabase Storage buckets. Products can have multiple photos (`products.image_urls TEXT[]`, first item = cover/`image_url`), shown via `ProductGallery.tsx` (product page) and `MiniCarousel.tsx` (store cards, auto-advances every 2.5s).
- **Product reels**: `components/ui/ProductsReel.tsx` is the auto-scrolling horizontal carousel (`animate-reel` in `tailwind.config.ts`, pauses on hover) used for "Productos Destacados" on the home page and for each business's own "Productos" section. Optional `stock_quantity`/`is_available` on each item show an "Agotado" badge (disables `AddToCartButton`) or "Últimas X" near the price — callers that don't pass them keep the old behavior (no badge). Nav arrows call `scrollBy({behavior:"smooth"})` but must pause the auto-scroll ref first, or the per-frame `scrollLeft` write cancels the smooth scroll almost instantly. Cards no longer show a category badge (removed 2026-09-14, every screen that uses this component) — the category is only shown on the product's own detail page now. The title reserves 2 lines (`min-h-[2.5rem]`) and the "Agregar al carrito" button sits at `mt-auto` inside a `flex flex-col` card, so a 1-line title doesn't leave that card's button sitting higher than its neighbors in the same grid row.
- **Categories (rewritten 2026-09-21, was a fixed list): dynamic table with parent/child hierarchy, ported from a sibling project's behavior ("Orden Express", `C:\nube` — outside this repo).** `supabase/categories.sql` (table `categories`: `id UUID`, `name`, `parent_id` self-reference, two case-insensitive partial unique indexes — one scoped to roots, one scoped per parent, seeded with the original 17 root names). `src/lib/categories.ts` (`normalizeCategoryName`, `buildCategoryTree`, `findOrCreateCategory`, `getCategoryTree`) and `src/lib/hooks/use-categories.ts` (`useCategories()` for client components). Storage stays a plain **name string** everywhere (`businesses.category`, `products.categories[]`) — never an id — specifically so nothing that already filters by name (`.contains()`, `/category/[name]`, chip rows) needed to change. No food/restaurants; only services and physical products.
- **`src/components/ui/CategoryPicker.tsx`**: the picker UI — an autocomplete combobox per level (parent, optional child) with inline "+ Nueva" to create a category on the fly (any authenticated seller can, no admin moderation/request queue like the source project has — deliberately not ported, not asked for). `mode="single"` (one pick, used by `crear-tienda`/`settings` with `allowSubcategory={false}` — a business only gets a **root** category, never a child, because `/category/[name]` matches `businesses.category` by exact `.eq()`, not hierarchically) vs `mode="multi"` (several removable picks, used by the product form — when a child is picked, `picksToNames()` stores **both** the parent's and the child's name in `products.categories[]`, so existing parent-level browsing keeps finding the product). `namesToPicks()` does the reverse for editing — merges a stored child name with its stored parent name back into one pick, not two.
- **Real bug (2026-09-21): creating a new category from the single-mode picker saved the row but never applied the selection.** The `onChange` handler resolved the picked ids to a name *synchronously*, in the same event-handler tick as `onCategoryCreated` — but that name lookup used the caller's `tree`, which was still the pre-creation snapshot (the `useCategories()` state update from `onCategoryCreated` hadn't flushed yet). Fixed by never resolving a pick to a name inside `onChange` — store the `CategoryPick` (ids) in state and resolve to a name lazily, only at save time, matching the pattern the product form's multi-mode already used successfully. Rule of thumb: a picker `onChange` should only ever store ids, never dereference `tree` synchronously to produce a display name.
- **`BUSINESS_CATEGORIES`/`CategorySelect.tsx` are gone (deleted 2026-09-21)** — replaced end-to-end by the above. If you're reading an old comment or memory that references either, it's stale; use `CategoryPicker`/`useCategories()`/`getCategoryTree()` instead.
- **Prices**: Always formatted with `formatPrice()` from `src/lib/utils.ts` (es-MX locale, MXN currency).
- **User geolocation**: `src/lib/user-location-context.tsx` (`UserLocationProvider`, mounted once in `(public)/layout.tsx`) asks for browser geolocation once per session and shares it via `useUserLocation()`. `BusinessCard` uses it with `distanceKm()`/`formatDistance()` (`utils.ts`) to show distance next to the address; silently shows nothing if permission is denied.
- **"Ver en el mapa"**: business cards and the product page link to `/map?business=<id>`. `BusinessMap.tsx` (Leaflet) reads `focusId`, centers on that business at zoom 17, and auto-opens its popup with a highlighted (orange) marker. Same `focusId` prop plumbed through `BusinessMapGoogle.tsx`/`MapWrapper.tsx` for when a Google Maps key is configured.
- **Product search across stores**: `(public)/page.tsx`'s `getProductSearchResults()`/`getDemoProductSearchResults()` search `products` (not just `businesses`) when there's a text query, rendering a "Productos que coinciden" section above the business results. `SearchBar.tsx`'s autocomplete also suggests matching products (not just businesses/categories), each linking straight to `/product/<id>`.
- **Reviews require a delivered order**: `ReviewSection.tsx` posts to `/api/reviews` (not a direct client insert) — that route checks Clerk `auth()` **and** that the user has an `orders` row with `status = 'entregado'` for that business before allowing the insert. The UI shows a "Compra verificada" badge when eligible, or a lock message when logged in without a delivered order.
- **Business trust metrics**: `src/lib/business-metrics.ts` — `getOrderCompletionRate()` (% delivered among resolved orders, `null` if none yet, never a false 0%) and `getAverageResponseTime()` (time from a buyer's first message in a conversation to the seller's first reply, averaged across conversations). Shown as chips next to the star rating in `business/[id]/page.tsx`.
- **Admin mutations must go through an API route, never a direct client-side `supabase.from(...).update()/.delete()`.** Since RLS is disabled, a hidden button is the only client-side gate — with no server check, anyone holding the anon key could call the same mutation directly against Supabase's REST API. Follow the pattern in `/api/admin/businesses` and `/api/admin/users`: `auth()` for a real Clerk session, then `profiles.role === "admin"` fetched server-side, *before* touching the target table. `/api/admin/coupon-credits` was the original example of this pattern.
- **Reverting a demoted owner's role must check their *current* role first.** The old `revert-owner-role.ts` (now inlined in `/api/admin/businesses`) set `role = "client"` whenever a business owner had zero businesses left, with no check for what their role actually was — this demoted an **admin** to `"client"` when an admin created and then rejected their own test business (real incident, 2026-09-11; the account was restored via `supabase/restore-admin-role.sql`, run 2026-09-15). Only revert `"business"` → `"client"`; never touch `"admin"`.
- **`profiles.role` only becomes `"business"` on approval, not on creating the store (fixed 2026-09-15, real issue).** It used to flip in `/api/businesses` (POST) the moment someone created a business, so a still-pending seller already showed the "Business" badge and the seller nav switcher before any admin had looked at their request. Now `/api/businesses` leaves the role untouched, and `/api/admin/businesses`'s `"approve"` action is what sets it to `"business"` (skipping admins, same guard style as the `"delete"` revert above). Because dashboard access and the "Mi cuenta"/"Mi tienda" switcher used to key off that same role, they needed their own fix too — see the `useAuthUser()`/`hasBusiness` bullet below and `dashboard/layout.tsx`'s access check, which now grants entry (with `PendingApprovalGate` still blocking everything except `/dashboard/business/settings`) to anyone who **owns** a business row, approved or not, instead of checking `role === "business"`.
- **`useAuthUser()` (`src/lib/hooks/use-auth-user.ts`) exposes `hasBusiness`: owns ≥1 business row, regardless of approval.** Use this — not `role === "business"` — to decide whether to show seller-facing nav (the "Mi cuenta"/"Mi tienda" switcher in `DesktopSidebar.tsx`/`Navbar.tsx`/`MobileNav.tsx`/`mas/page.tsx`/`perfil/layout.tsx`, and `UserInfo.tsx`'s own separate query), so a pending seller can still reach their store's settings from the normal nav, not just by knowing the raw URL. Always compute it as `role !== "admin" && (role === "business" || hasBusiness)` — an admin who also happens to own a business (the 2026-09-11 incident) must keep seeing "Mi panel", never the seller switcher. Two things stay keyed to the *real* `role === "business"` on purpose and must not switch to `hasBusiness`: "Ver mi tienda como la ven los clientes" and "Compartir mi tienda" in `UserInfo.tsx` — the public store page 404s for everyone, owner included, until approved (see `business/[id]/page.tsx`'s `.eq("is_approved", true)`), so offering either link pre-approval would just be a broken link.
- **`DashboardNav.tsx`'s menu (and `dashboard/layout.tsx`'s mobile bottom nav) must not list seller pages while the store is pending (fixed 2026-09-15, real issue).** `PendingApprovalGate` already blocked the *content* of every page except `/dashboard/business/settings`, but the menu itself still listed all of them (Resumen, Productos, Pedidos, Cupones, Escáner QR, Mensajes, Preguntas, Notificaciones, Reseñas, Estadísticas) — revealing the seller panel's full structure to an account nobody has approved yet. `DashboardNav` now takes a `pendingApproval` prop (passed from `dashboard/layout.tsx`, which already computes it) and renders only the Configuración item when true; the mobile bottom nav's inline array got the same filter. Any new item added to `DashboardNav`'s `navItems` is automatically covered by this filter — no per-item change needed. **Desktop and mobile intentionally differ here (2026-09-18):** the mobile bottom nav's pending array also has "Inicio"/"Buscar" (links to the public site) alongside Configuración, so a pending seller doesn't feel trapped — but `DashboardNav`'s desktop `pendingItems` was asked back down to just Configuración, by explicit user choice. Don't "fix" this asymmetry without checking first; it's deliberate, not a leftover bug.
- **Real bug (2026-09-18): `MobileNav.tsx`'s last tab (perfil/tienda) flashed through three different icons on every page load.** Its icon was decided from `userId`/`role`/`hasBusiness` without checking `loading` from `useAuthUser()` first — since Clerk resolves `userId` before Supabase resolves `role`/`hasBusiness`, a logged-in seller would briefly see the "not logged in" `User` icon, then the "loading" `Menu` (three lines) icon, before settling on `Store`. `Navbar.tsx`/`DesktopSidebar.tsx` never had this bug because they already gate their whole user block on `!loading`. Fixed by checking `loading` first: `!loading && !userId ? User : actingAsSeller ? Store : Menu` — never claims "logged out" while still loading.
- **`UserInfo.tsx`'s seller icon showed the generic `Store` icon, never the business's real logo (fixed 2026-09-18, real issue).** `activeBusiness` state was typed narrower than the actual `Business` row it holds (`loadOwnedBusinesses` returns the full row, including `image_url`, but the `useState` type only listed `id`/`name`). Widened the type to include `image_url`/`is_approved` and render `<Image>` when `image_url` exists, falling back to the `Store`/`User` icon otherwise. Applies to both the sidebar and topbar variants since they share this component.
- **Sucursales (branch locations, added 2026-09-18): a branch is just another address of the same business, not an independent store.** It shares products, coupons, category, and logo with its "parent" `business_id` — only name/address/coordinates/an optional WhatsApp are its own. New table `business_branches` (`supabase/business-branches.sql`, **not yet run** — DDL, needs the Supabase SQL Editor), created/deleted through `/api/business-branches` (ownership-checked server-side, same pattern as other owner-mutation routes). "Agregar nueva sucursal" sits next to "Agregar otra tienda" in `UserInfo.tsx`/`Navbar.tsx`/`dashboard/business/settings/page.tsx`, gated on the active business already being **approved** (nothing to share before that). The creation form (`(public)/perfil/crear-sucursal/page.tsx`) resolves the active business via the same `current_business_id` cookie `settings/page.tsx` already uses. On the map (`BusinessMap.tsx`/`BusinessMapGoogle.tsx`/`MapWrapper.tsx`/`map/page.tsx`) each branch is its own pin with a distinct `id` (so `focusId` can target it unambiguously) but a `businessId` field the popup's "Ver negocio →" link uses instead, so it always lands on the parent's page. The parent's own public page (`business/[id]/page.tsx`) lists its branches under "Otras sucursales". **Known gap:** `UserInfo.tsx`'s desktop sidebar dropdown only opens when the owner has more than one business (`canOpen = isTopbar || hasMultiple`), so with a single store neither "Agregar otra tienda" nor "Agregar nueva sucursal" are reachable from there — not fixed, since both are already reachable from Configuración; flagged in case the dropdown's `canOpen` gate should change.
- **Image crop + WebP upload**: `src/components/ui/ImageCropUpload.tsx` — Facebook/Instagram-style fixed-aspect crop (`react-easy-crop`) + zoom, converts to WebP via `canvas.toBlob(..., "image/webp", 0.85)` (falls back to whatever the browser actually returns — check `blob.type`, never assume WebP encoded). Supports drag-and-drop onto the upload zone in addition to the file picker, and shows the exact output size (`outputWidth`×`outputHeight`) as a hint. Used for both logo and banner in `crear-tienda/page.tsx` and `dashboard/business/settings/page.tsx`.
- **Real bug (2026-09-21): the product form's multi-photo uploader had no drag-and-drop, only click-to-browse.** `dashboard/business/products/page.tsx`'s "Agregar foto" tile was missing the `onDragOver`/`onDragLeave`/`onDrop` handlers that `ImageCropUpload.tsx` already had for the single logo/banner uploader. Fixed by adding the same pattern to the tile (reusing the existing multi-file `addFiles()`, no change to that function itself) plus the same "o arrastra aquí" hint and highlight-on-drag-over styling. When adding any new file-drop zone, check `ImageCropUpload.tsx` first — it's the canonical pattern in this codebase, and it's easy to add a second uploader that only handles click.
- **Real bug (2026-09-21): dragging an already-uploaded product photo onto the "Agregar foto" tile duplicated it.** The thumbnails render via `next/image`, which by default lets the browser natively drag the rendered `<img>` — dropping that native image-drag onto a zone with an `onDrop` handler also populates `dataTransfer.files` in Chromium, so `addFiles()` added it a second time as if it were a brand-new file. Fixed at the root: each thumbnail's `<Image>` now has `draggable={false}` and `pointer-events-none`, so it can never be natively dragged as a file at all — only the *wrapping* `<div>`'s own `draggable`/`onDragStart`/`onDrop` (added for reordering, see below) can initiate a drag, and that path is tracked via a `draggingImageIndex` state the drop handlers check to tell "reordering an existing photo" apart from "dropping a new external file". Same root cause would bite any future feature that both renders draggable `<img>`s *and* has a file-drop zone nearby — disable native `<img>` dragging (`draggable={false}`) whenever a custom drag interaction is layered on top of it.
- **Product photos are draggable to reorder (added 2026-09-21) — whichever ends up first is the cover, same `i === 0` "Portada" logic as before.** `moveImage(from, to)` in `dashboard/business/products/page.tsx` splices the `images` array; dropping one thumbnail onto another swaps their position, dropping one onto "Agregar foto" moves it to the end.
- **Product photos are converted to WebP before upload (added 2026-09-21, same as the business logo/banner already were via `ImageCropUpload.tsx`, product photos previously weren't).** `convertToWebp()` in `dashboard/business/products/page.tsx`: HEIC (iPhone photos) go through `heic-convert/browser` to JPEG first (canvas can't decode HEIC directly), then everything goes through a canvas → `toBlob(..., "image/webp", 0.85)`. Falls back to uploading the original file untouched if conversion throws for any reason — never blocks publishing a product over this. Extension/`contentType` at upload time are read from the resulting `blob.type`, never assumed to be `.webp` (same rule as `ImageCropUpload.tsx`, since the browser can fall back to png).
- **`.no-spinner` utility class (`globals.css`, added 2026-09-21)**: hides the native up/down arrows on `<input type="number">` (`appearance: none` on the WebKit spin-button pseudo-elements, `-moz-appearance: textfield` for Firefox). Added because the app's stepper arrows are useless when a quantity/price is always typed directly, never incremented one click at a time — apply to any future numeric input with the same expectation.
- **Precio (price) field shows a gray "ghost" of the missing decimals while typing (added 2026-09-21) — e.g. typing `123` shows a faded `.00` right after it; typing `123.34` shows nothing, since it already has 2 decimals.** `dashboard/business/products/page.tsx`'s `priceGhostSuffix(raw)` computes exactly what's missing to reach 2 decimal places. A `type="number"` input can't reliably overlay ghost text after the caret, so the field is `type="text"` + `inputMode="decimal"` (still shows the numeric keyboard on mobile) with a manual `/^\d*\.?\d*$/` filter on input, layered under an absolutely-positioned decoy div containing the same typed text in `invisible` (to reserve its exact pixel width) followed by the visible gray ghost suffix — the classic "ghost autocomplete inside an input" CSS trick. Purely cosmetic: what actually gets saved is still whatever `parseFloat()` makes of the raw typed string, same as before.
- **Real bug (2026-09-22): the product card's description showed in full instead of clamping to 2 lines.** `dashboard/business/products/page.tsx` had `line-clamp-2` on the same element as a separate `sm:block` — Tailwind bundles several CSS properties (including the `display` value it needs) into `line-clamp-N` as one unit, and the loose `sm:block` was overriding just that piece, leaving the rest of `line-clamp-2` (like `-webkit-line-clamp`) applied but inert. Fixed by removing the separate `sm:block` and using `sm:line-clamp-2` alone, so the responsive variant carries both "become visible" and "clamp" together. Confirmed via `getComputedStyle` (height dropped from 1020px to 40px). Any future `line-clamp-N` combined with a plain `block`/`sm:block` on the same element has this same silent-breakage risk.
- **`dashboard/business/products/page.tsx`'s "Mis Productos" list is paginated (added 2026-09-22): `PRODUCTS_PER_PAGE = 50` (5 cols × 10 rows).** `page` state resets on tab/filter change; `currentPage = Math.min(page, totalPages)` self-corrects if a deletion shrinks the list below the current page. Anterior/Página X de Y/Siguiente controls only render when `totalPages > 1`.
- **Storage buckets have their OWN policy system, separate from the (disabled) table-level RLS (discovered 2026-09-22, real bug).** The app disables RLS on every Postgres table because auth is Clerk, not Supabase Auth (see `clerk-migration.sql`) — but Supabase **Storage** buckets are governed by their own, independent policies, and those were never touched. Confirmed via direct `curl` against the Storage REST API: the `product-images` bucket grants `anon` only `INSERT`/`SELECT` — a `DELETE` with the same anon key the rest of the app uses returns `403 Access denied`. This meant deleting a product (or removing a photo while editing one) silently left its files behind in Storage forever; a first fix attempt (calling `.remove()` from the browser's anon-key client) failed with no visible error at all, which is what made this easy to miss.
- **Fix pattern for the above: `src/app/api/products/route.ts`, using a service-role Supabase client (`createClient` from `@supabase/supabase-js` directly, with `SUPABASE_SERVICE_ROLE_KEY`) specifically for Storage deletes, never for anything table-level (tables don't need it, RLS is already off there).** `DELETE` (full product removal): Clerk `auth()` check, ownership check via the *regular* anon-key server client (fetch the product, confirm `businesses.owner_id === userId`) before ever touching Storage, then best-effort `storage.from("product-images").remove(paths)` with the service-role client (a failed removal only `console.error`s, never blocks deleting the product row itself), then deletes the row. `POST` (used when *editing* a product removes/replaces a photo without deleting the product): same ownership check, takes `{ product_id, urls }` and removes just those specific paths — `dashboard/business/products/page.tsx`'s `handleSave` computes `urls` itself by diffing the product's *original* `image_url`/`image_urls` (captured when the edit form opened, from `editing`) against the final list actually being saved; anything present before but missing now gets sent here right after the update succeeds. Any future feature needing to delete or replace a Storage file must go through a route like this one — never a direct client-side `.remove()` call, it will silently no-op.
- **Real bug (2026-09-22): product photos looked cropped everywhere — a tall/narrow photo (e.g. a necklace) lost its top and bottom, showing only a middle sliver.** Every product-photo thumbnail used `object-cover` inside a fixed-size (usually square-ish) box, which crops whatever doesn't fit to fill the box completely — fine for photos close to the box's own aspect ratio, destructive for anything far from it. User picked "show the full photo always" (over "only fix new uploads by padding to a square canvas at upload time") specifically because it fixes every already-uploaded photo retroactively, with no reseller needing to re-upload anything. Fixed by switching `object-cover` → `object-contain` (paired with a light neutral background on the container, so a photo that doesn't fill the box doesn't leave a jarring gap) in the 5 places a product photo renders as a thumbnail or main image: `dashboard/business/products/page.tsx` (the edit-form thumbnails and each product's card in "Mis Productos"), `components/ui/ProductsReel.tsx` (home "Productos Destacados" + a business's own "Productos" section + `/productos`, all the same component), `(public)/product/[id]/ProductGallery.tsx` (main image + desktop/mobile thumbnail rails), and `components/ui/CartDrawer.tsx` (cart line-item thumbnail).
